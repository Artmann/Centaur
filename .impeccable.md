# Impeccable

Design context for Centaur, used by the design skills. Written from a session with the project
owner; update it here rather than re-deriving it from the code.

## Design Context

### Users

Developers on Windows, in their shell all day. They came to Centaur because it is fast and because
it looks good without configuring anything — those are the two promises the README makes. Their
context is a maximised or half-screen window that stays open for eight hours behind an editor.

The job to be done in the terminal is *get the command run and read the output*. The job in the
application surfaces — settings, tab strip, reverse search, command palette — is different and
much rarer: *change one thing and get back out*. Nobody browses Centaur's settings for pleasure.
A visit is a task with a known end.

### Brand Personality

**Fast, calm, trustworthy.**

- **Fast and precise** — a sharp instrument, nothing between intent and result. Speed is what the
  README leads with, so latency and jitter are brand problems, not just performance problems.
- **Calm and refined** — considered and quiet, easy on the eyes across a long day. Catppuccin's
  whole premise, and the reason the app ships with it.
- **Trustworthy and solid** — never loses scrollback, never surprises you, defaults you can rely
  on without configuring. Every setting writes through immediately; there is no apply or cancel
  step to doubt.

Not: playful, loud, or witty for its own sake. Copy is plain and says what happens.

### Aesthetic Direction

**Quiet identity.** The application surfaces take the shape every desktop app has settled on — a
full-height sidebar, a page heading, sections of grouped rows — so nobody has to learn where
anything is. Within that familiar skeleton, the palette, the spacing rhythm and one or two
details make it read as *this* app rather than as a template.

- **References**: the Cursor and Granola settings screens — sidebar, sentence-case section labels,
  one card per section, small controls on the right of each row.
- **Anti-references**: a settings page that looks like terminal output. Monospace labels, terminal
  chrome and terminal-sized controls on an application surface are the specific failure this
  project already hit and corrected once.
- **Theme**: both, and neither is the default. All four Catppuccin palettes (Latte, Frappé,
  Macchiato, Mocha) are first-class; Macchiato ships selected. Any colour decision that only works
  on a dark background is a bug.
- **Type**: JetBrains Mono belongs to the terminal. Application surfaces use the system UI stack.
  Monospace on an application surface is reserved for values that *are* code — a shell command, a
  path — and is a deliberate signal, not a default.

### Design Principles

1. **The terminal is the product; the chrome is a doorway.** Application surfaces earn attention
   by being quick to leave, not by being interesting. Optimise for time-to-exit.
2. **Everything is themed from the terminal's palette.** Chrome colours are derived from the
   active `TerminalTheme`, never hardcoded. One formula must work on all four palettes — blend
   towards the foreground rather than picking a palette entry, so it lightens on dark and darkens
   on light.
3. **Familiar skeleton, considered detail.** Never invent a novel layout for a solved problem.
   Spend the design budget on rhythm, contrast and the small states instead.
4. **Meaning never rides on colour alone.** Selected, on/off and error states must read without
   the accent hue — an outline, a dot, a position, a word. Latte's accent is low-contrast, and
   that is the honest test case.
5. **Keyboard-complete, with visible focus.** This audience lives on the keyboard. Anything the
   mouse can do, the keyboard must do, and the focused element must be obvious. Text must clear
   WCAG AA (4.5:1) on all four palettes.
6. **Write through, say so plainly.** No apply/cancel. Copy states what happens and when — "applies
   to panes opened from now on" — and errors say what to do about it, naming the place to fix it.
